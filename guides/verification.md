# Independent verification and material review

Read the accepted requirements, applicable guides and the exact candidate. Bounded deliveries use one independent reviewer covering requirements and standards by default; completed issue submissions use the two roles in [review](review.md), loaded at that boundary. Choose the provider and model under the project's model policy ([models](models.md)). Under `model_policy.verification` (default `different_vendor`) the verifier comes from a different vendor than the builder. The verifier reads the original requirements and the exact artifact itself; self-review or acceptance on the lead's conclusion alone does not count. Model choice never lowers required coverage. Add further reviewers only for distinct consequential risk. Read [UI testing](ui-testing.md) for frontend exercise, [integration](integration.md) for combined deliveries or [records](records.md) for record checks, and load [child submission](submission-child.md) only when returning the result.

## Before checking

After a restart, restored context or interruption, reread the current status record before starting another executable check, build or launch. Reconfirm the exact source, host, dependencies, current authority, deadline and resource allocation. Availability does not renew a spent grant or clear a later hold. If an original run is still live, preserve it and reconcile only its already-authorised waits; do not start a replacement run or cleanup. If current authority cannot be established, return the blocker without executing anything.

State the acceptance requirement each check proves, the exact source or build pin, affected dependencies, the fixture and permitted effects. Expected results come from accepted requirements, not the current implementation or an author's changed test. If the diff touches existing tests, review those edits before trusting a passing gate: unbriefed edits to existing tests, loosened assertions (such as exact matches relaxed to truthy or substring checks, or broadened error types) and newly skipped or disabled tests count as contract violations, not fixes. Walk the diff for generated-code failure modes that pass green suites: hardcoded success returns, broad catch-all blocks that swallow errors into defaults, duplicate local idioms beside existing ones, uncalled parameters or flags, and tests that mock internal functions instead of exercising the real boundary.

Fixtures must use the real application constructors, schema or serialisation shape at the affected boundary, with representative state and relationships. Synthetic values remain synthetic; mock only the declared external effects. If a fixture bypasses the failing path or cannot represent the required state, block that check and assign its repair owner. Never silently replace a missing dependency with a stub and claim integration coverage.

Keep source fixed through the run; identify uncommitted changes and the loaded build. Confirm the delivered candidate matches the tested source. Changed relevant dependencies require targeted retesting. Reuse unchanged qualified evidence rather than rerunning everything.

## Evidence and decisions

- Exercise the normal flow and its resulting state, not just the presence of UI or a successful construction. Cover affected denied roles, invalid input, persistence, cancellation, failure, retry and duplicate-effect boundaries. Retain the necessary security and lifecycle checks.
- For a regression, show that the meaningful assertion fails against the faulty behaviour and passes after the correction where feasible within authority. If the before run cannot be performed, say why and mark the regression claim NOT RUN or partial. That blocks Done when regression proof is required, unless the accepted assignment explicitly waives it; a reviewer cannot waive it to obtain a pass. Never change an expected result merely to match the defect.
- Use the project's configured test, lint, typecheck and build commands. Broaden only for required or affected boundaries.
- For agent behaviour, cover instructions, tools, permissions, triggers, UI response, continuation and subagent delivery. Prompt or control edits alone do not qualify runtime behaviour.
- Report each affected requirement as PASS, FAIL, BLOCKED or NOT RUN with the command or action, observed outcome and evidence. Skips, baseline failures, unavailable fixtures and unrun gates cannot count as passes. Explain whether a known baseline affects the acceptance claim, and give recurring blockers one repair owner.
- Findings state the requirement, location, trigger, consequence and reproduction. Return consequential ambiguous semantics to the owning lead. Preserve earlier failed receipts.

Review passes only when the assigned requirements and standards are met, meaningful required checks pass on the delivered candidate, blocking findings are resolved and evidence supports the claimed scope. A source-only review may pass its source assignment while runtime acceptance is BLOCKED; never label that overall issue Done.

Fixes belong to the lead unless the task explicitly authorises owned corrections. A fresh review round gets the original brief and prior unresolved findings. Retest affected behaviour after fixes; stop redundant rounds without changed inputs, unresolved findings or required checks. Keep source, synthetic, native, platform, provider and human evidence separate. Report compactly to the parent with exact pins, result, findings and remaining gates.

## Review rounds and scope

Cap independent review at three rounds per deliverable unless project policy sets another number, and stop earlier when a round finds nothing above Minor. A third round that still finds a Critical or Major issue goes to the lead and orchestrator as a design question, not a fourth automatic round; an unresolved Critical or Major finding on a mandatory boundary below still blocks Done. Independent review stays mandatory for the boundaries that hurt if wrong: accounts, authentication, permissions, private data and anything that deletes data. For purely visual polish that touches none of those boundaries, rely on the lead's own automated checks and the user's acceptance, not extra review rounds. A failure of the review method itself (output or read limits, reading plans, quoting or parsing errors) is a process cost to repair once, not a reason to add a round or loosen a check. None of this waives a required check or lowers an acceptance gate.

Run one short global review before the first external release (or the project's configured release stage), limited to the high-risk boundaries above plus an integration check of the joined candidate. After that release, review from reported bugs and user findings. Run the full global review before general availability.
